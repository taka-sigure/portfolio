プロジェクト実績

1. ファネル分析とUX改善

2025年6〜8月：横型フォームへの改修 ／ 2025年12月〜2026年3月：追加改善

課題
オーガニック流入が約1/3に減少。フォームの転換率改善が必要だった。
担当
計測基盤の修正、ユーザー行動の分析、フロントエンド・バックエンドの設計・実装、効果検証。
成果
フォームCVR 1.5% → 5.0%（約3.3倍）。主要成約件数の前年同期比 -13% → +30%。

マッチングプラットフォームにおいて、外部要因（SEO順位低下など）によりオーガニック流入が約1/3へ減少した局面での取り組み。 流入獲得側は別部門・外部要因の比重が大きかったため、コントロール可能なフォーム側のコンバージョン最適化に注力した。

計測基盤の修正

当初のログにはクローラーやボットのアクセスが混入しており、CVRの分母・分子が歪んでいた。 改善施策に先立ち、ボット除外ロジックの実装やGoogle Tag Manager (GTM)・Meta Pixelなどのタグ発火タイミング・カスタムイベント設計を整理し、正しい数値を計測できる土台を作った。

施策の変遷と学び

  • 施策1: 横型ステップフォーム化 (1.5% → 2.5%)
    ヒートマップツール（Clarity）の定性ログから、既存の縦型埋め込みフォームがファーストビュー外でスクロールされず見られていないことを確認。 海外の同業サービスを参考に、1問1答形式の横型ステップフォームを設計・実装して初期改善を得た。
  • 失敗と方針転換
    フォーム終盤の個人情報入力ステップで約25%が離脱していたため、「サイトへの信頼不足」と仮説を立て、認証マークやメディア掲載実績を追加した。 しかし数値に有意な改善は見られなかった。
    この結果から、離脱の主因は信頼性ではなく「個人情報を入力して渡すこと自体の心理的コスト」にあると判断。「信頼を足す」アプローチから「ユーザーへの要求を減らす（削る改善）」へと方針を転換した。
  • 施策2: アドバイザー1人の確認に簡略化 (2.5% → 5.0%)
    ファネル分析の結果、詳細なマッチング相手の選択ステップの通過率が20%程度と極端に低かった。 「ユーザーは自ら細かく選びたいのではなく、適切な候補を提示してほしい」と仮説を立て、あらかじめ推奨アドバイザー1人を選択状態にして確認（Yes/No）のみに簡略化。 ステップ通過率が20%から35%に改善し、最終CVRは5.0%に達した。

結果と検証設計

フォーム開始から送信完了までの全体CVRは1.5%から5.0%へ改善（約3.3倍）。 主要成約件数は、施策前の前年同期比 -13% から、施策後は +30% へ反転した。 月商約1,000万円規模の対象サービスにおいて、流入減少下での売上防衛・機会損失の抑制に寄与した。 効果検証においては、広告キーワードを固定したスプリットテストにより季節性や流入質の変動を排除し、リリース日が月半ばであったため過渡期の月を除外して評価を行った。

2. レガシーAPIの段階移行と設計改善

2026年3月〜現在 · 移行中

課題
.NET 6のサポート終了への対応と、責務が混在したAPIの保守性改善。
担当
移行の提案、バックエンド・フロントエンド・インフラの設計・実装、新旧APIのDB互換性の確保。
進捗
新旧APIの並行稼働とルーティング切り替えによる段階移行を継続。ドメインロジックを独立させ、テストを作成しやすい構造へ。

長年の運用でビジネスロジック・アプリケーション処理・インフラ処理の責務が混在し、影響範囲の把握やテストが困難になっていた.NET 6製APIの刷新。

背景と合意形成

コードの設計改善（DDD化）単体では事業的な優先順位が上がりづらかったため、フレームワーク（.NET 6）の公式サポート終了(EOL)というビジネスリスクと紐づけて提案し、リファクタリング工数を確保した。 最終的なLTS（.NET 10）への差分を小さく抑える中継地点として、当時最新の.NET 9を採用した。

移行設計とリスク管理

  • Blue-Green型の並行構築:
    インプレースでの更新は避け、.NET 9 + DDD構成の新規サービスを別系統として並行構築。 フロントエンド側のルーティング切り替えで移行することで、問題発生時の即時ロールバック性を確保した。
  • データベース共有時の互換性担保:
    新旧サービスが同一のデータベース（Aurora MySQL）を参照する並行稼働期間中、マイグレーションの実行権限を新規サービス側に一本化。 スキーマ変更は加算的な変更（新規テーブル作成、NULL許容またはデフォルト値を持つカラムの追加）に限定し、破壊的な変更（カラム削除・型変更）は旧系統の完全廃止まで持ち込まない運用ルールを敷いた。

現在の進捗

2026年3月から移行を進めており、現在も新旧APIを並行稼働させながら段階的な切り替えを継続している。 ドメインロジックの独立により、単体テストを作成しやすい構造へ改善。旧系統の完全廃止までは、DBスキーマの互換性を維持する方針としている。

3. 自動テスト・CI/CD環境の整備とチーム支援

課題
開発速度を維持しながら、変更時の品質確認とチームの立ち上がりを支える。
担当
Vitest・Playwrightの導入、GitHub Actionsの整備、インターンのメンタリング・コードレビュー。
成果
手動リグレッション確認の負荷を低減し、自動検証・デプロイとオンボーディングを支援。

開発速度と品質を両立させるための自動化基盤およびチーム支援の取り組み。

  • フロントエンドテスト自動化:
    Vitest による単体・コンポーネントテスト、Playwright による主要ユーザー導線のE2Eテストを導入。変更時のデグレード（先祖返り）を早期検知し、手動リグレッション確認の負荷を低減した。
  • CI/CDパイプライン運用:
    GitHub Actions を用いて、Lint、自動テスト、ビルド検証、ステージングおよび本番環境へのデプロイワークフローを自動化。安全なリリースフローを維持。
  • メンタリングとコードレビュー:
    インターン生のメンターを担当し、タスクの分解や設計相談、コードレビューを実施。実装品質の担保とともに、早期の自律的な開発立ち上がりを支援した。

4. 計測基盤の整備とデータ活用

課題
アクセスのノイズやイベント計測の不整合により、施策評価の土台が不十分だった。
担当
ノイズの除去、イベント発火タイミングの正常化、BIツール・SQLによるダッシュボード整備。
成果
開発者以外のメンバーもKPIの進捗やファネルの離脱ポイントを確認できる環境を整備。

施策評価や日常運用のためのデータ基盤整備。 分析ツールの数字をそのまま信用せず、ノイズ（クローラー、社内アクセス）の除去やイベント発火タイミングの正常化を先行して実施した。 また、SQLによるダッシュボード整備を通じて、開発者以外のメンバーも直接KPIの進捗やファネルの離脱ポイントを確認できる環境を整えた。
