Case Study 01 // Product Growth
Funnel Optimization Behavioral Analytics AB Testing Data Platform

外部流入減少を跳ね返すファネル最適化 (CVR 1.5% → 5.0%)

SEO低下によるオーガニック流入減少に伴い、主要KPIが前年比マイナスへ沈む局面において、自分がコントロールできるコンバージョン側に集中。計測基盤の適正化から行動ログ分析、2段階のフォーム刷新を実施し、前年比+30%への反転成長を達成しました。

初期状態: 縦型埋め込みフォーム (ノイズ混入・未到達) 1.5%
施策1: 計測基盤修正 + 横型ステップフォーム化 2.5% (+67%)
施策2: 選択プロセスの自動化 (心理的負荷の削減) 5.0% (+233%)
🔍 課題特定と計測の適正化
  • 計測先行の徹底: 既存ログにボット等のノイズが混入していたため、施策より先に除外フィルタを実装し、正しい数字が測れる環境を担保。
  • 定性データの活用: ヒートマップ（Clarity）により、従来のフォームがスクロールされず見られていないことを特定。先進UXを参考に1問1答形式へ刷新。
💡 失敗から得た「削る改善」への転換
  • 仮説の誤謬: 最終入力ステップの25%離脱に対し「信頼不足」と仮説を立て、認証マーク等のトラストシグナルを追加するも有意差なし。
  • 思考の転換: 離脱の主因は信頼ではなく「情報入力自体の心理的負荷」と看破。「信頼を足すより、要求を削る」方針へ転換し、選択ステップの自動化を断行。
📈 定量成果 & 検証の誠実さ
  • KPI反転: 請求成約件数を前年同期比 -13% から +30% (43pt反転) に改善。年間億規模の売上消失を防衛。
  • 交絡因子の排除: キーワードを固定した媒体側スプリットABテストで季節要因を排除し、リリース混在月を自ら除外して客観的に効果測定。
Case Study 02 // Modernization
C# / .NET 9 Domain-Driven Design (DDD) AWS Aurora Zero Downtime

レガシーAPIの.NET 9 + DDD化と無停止Blue-Green移行

長年の機能追加で責務が混在していたAPIを、.NET 6の公式サポート終了(EOL)という事業リスクを梃子にしてDDD構成でフルリファクタリング。同一データベースを共有する並行稼働期間を設け、ダウンタイムゼロでの切り替えを完遂しました。

🏛️ 組織を動かす技術判断
  • 工数の獲得ロジック: リファクタリング単体では事業価値が説明しづらいため、サポート終了期限という明確なビジネスリスクに設計改善を紐づけて合意形成。
  • バージョン選定: 最終目標（LTS）への差分を最小化するため、依存ライブラリの対応状況を踏まえ中継地点として最新バージョンを採用。
🛡️ デプロイ戦略によるリスク吸収
  • Blue-Green並行構築: インプレース更新のリスクをコードで背負わず、新規サービスとして並行稼働させフロントエンドの向き先切り替えで即時ロールバック可能に。
  • DB共有時の競合防止: マイグレーション実行権を新サービス側に一本化。スキーマ変更は加算的な変更（新規テーブル、NULL許容カラム）に限定し破壊的変更を凍結。
✨ 成果と将来への接続
  • 無停止移行: 本番ダウンタイムゼロ・無障害で世代交代を完了。
  • アーキテクチャの進化: ビジネスロジックをドメイン層に閉じ込めたことで単体テスト容易性が劇的に向上。後続のBFF導入の強固な基盤となった。
Case Study 03 // Architecture
AWS EventBridge Amazon ECS Terraform Datadog

定期ポーリングバッチからEventBridgeによるイベント駆動への移行

10分間隔の定期ポーリングでECSタスクを起動していた構成を、EventBridgeトリガーによるイベント駆動型アーキテクチャへ刷新。処理遅延をゼロにし、アイドル起動コストを削減しました。

⏱️ 課題の特定
  • イベント発生から最大10分の処理遅延が存在し、リアルタイム性が損なわれていた。
  • 送信対象が存在しない時間帯でも無駄にECSタスクが起動し、リソースとコストが非効率。
⚙️ 設計判断と移行
  • 既存資産の活用: Lambdaへ全面書き換えるのではなく既存.NETコンテナを活用できるECS実行方式を採用し、書き換え工数を最小化。
  • インフラのコード化: Terraformにより変更をコードレビュー可能にし、本番・検証環境の再現性を担保。Datadog監視をそのまま流用。
🎯 堅牢性の確保
  • DBステータス管理とトランザクションによる多重送信（二重処理）の完全防止。
  • EventBridgeのリトライポリシーと監視アラートによる耐障害性の確立。
Philosophy

エンジニアリング行動指針

技術選定やチーム主導において一貫して重視している価値観

📊

1. 計測を先に行う

施策に着手する前にノイズを除去し、正しく測れる基盤を整える。不確実な数値の上でいくら高度な改善を行っても正しい判断はできません。

✂️

2. 「削る」改善を尊ぶ

課題に対して機能やUIを足すのではなく、不要なステップや要求を削ることで摩擦を減らす。システムもユーザー体験もシンプルさが最大の武器になります。

🛡️

3. デプロイでリスクを殺す

複雑な変更のリスクをコードの慎重さだけで担保せず、並行稼働・向き先切り替え・即時ロールバックといったデプロイ戦略で構造的に安全性を確保します。

🤝

4. 技術を事業言語に翻訳する

リファクタリングやアーキテクチャ刷新の必要性を技術的正しさだけで主張せず、事業リスクや開発速度の向上に翻訳して合意を形成します。
